# Native renderer

The renderer replaces the guest GPU rather than emulating it, the way Kameo: RePowered and re:Blue do. The game's D3D library (XDK 2.0.20871, `d3d9ltcg.lib`) is statically linked into `default.xex`. Its entry points are named in `config/d3d.toml` and replaced with `REX_HOOK`, so the recompiled D3D bodies never run. Frames are drawn with [plume](https://github.com/renderbag/plume) (D3D12 on Windows, Vulkan elsewhere), and the game's Xenos shaders are translated offline by [XenosRecomp](https://github.com/hedge-dev/XenosRecomp). Both are submodules under `thirdparty/`.

There is no GPU plugin, not even as a fallback. `ReCherryApp::OnPreSetup` hands the SDK the renderer's `cherry::gpu::GraphicsSystem` (`src/gpu/`) through `RuntimeConfig::graphics`, and xenos is neither built nor staged. `--cherry_gfx_backend` picks `auto` (D3D12 on Windows, falling back to Vulkan), `d3d12` or `vulkan`.

The guest library's layout, signatures and call graph are in [../reverse-engineering/guest-d3d.md](../reverse-engineering/guest-d3d.md).

## Rules

* **Every D3D entry point the renderer handles is a `REX_HOOK`.** `REX_HOOK(D3DDevice_Swap, D3DDevice_Swap_hook)` marshals the guest registers into a typed host function. Marshal the LTCG signatures from guest-d3d.md, not the XDK prototypes: `ClearF`, `Resolve`, `DrawIndexedVertices`, `BeginTiling`, `EndTiling`, `Direct3D_CreateDevice` and `D3DQuery_GetData` all lost arguments. A float argument still uses up its GPR slot, so the hook takes a placeholder parameter for it, as re:Blue's `D3DDevice_Clear_hook` does.
* **No guest GPU.** Nothing consumes the command ring, so no interrupts are delivered and no read pointers are faked. The functions that wait are replaced instead: the ring is laid out so it never needs `KickOff`, the `BlockOnFence` and `BlockUntilIdle` hooks publish the CPU fence into the readback word at `*(dev+0x2B10)`, and `IsFencePending` answers from the render thread's progress.
* **No readback resolve.** Resolved surfaces are never copied back to guest memory for CPU code to read. Instead, a game function that reads a resolved surface on the CPU is hooked and given the result natively. In this game those functions are `RHIReadSurfaceData` (0x829809C0, screenshots and thumbnails), the occlusion query path (0x829802E0 → `D3DQuery_GetData`) and the texture-pool defragmenter's GPU memmove (0x82986B18), which becomes a CPU memmove plus host-texture invalidation.
* **State comes from the device shadow.** With LTCG, `SetRenderState`, most of `SetSamplerState`, `SetVertexDeclaration`, VB/IB `Lock` and `EndVertices` are inlined into UE3 and cannot be hooked. A draw hook reads render state, fetch constants, shader constants and bound objects from the guest `D3DDevice` at draw time (offsets in guest-d3d.md section (d)).

## Bring-up order

1. **Boot with no GPU** (in place). `src/gpu/hooks/ring.cpp`: `D3DDevice_SetRingBufferParameters` is a native `REX_HOOK` that lays the ring out as the original does, over one guest block nothing reads (4 MB of commands growing up, 12 MB of ring data carved down by the game's own carver `sub_829E8B70` through a custom allocator at `dev+0x3660`, its forced-KickOff threshold `dev+0x3BEC` raised), and skips the `Vd*` calls that would start a GPU. No frame reaches the ring limit and `Swap` rewinds it, so `D3D_RingBufferDeviceAllocate`, `D3D_CDevice_KickOff`, `D3D_CDevice_BlockOnPrimaryRange` and `D3D_CDevice_WritePrimary` are `REX_STUB`s. IDA shows every KickOff call site that uses its return value is behind the ring-limit test; UE3's own flushes call it and ignore the result, so the stub's warning appears about twice a frame. Every 600 presents the log reports the peak command and ring-data use in a frame. The waits, the waits (both `BlockOnFence`s, `BlockUntilIdle`, `IsFencePending`, `SynchronizeToPresentationInterval`, `sync.cpp`) and `Swap` (`present.cpp`) are hooked. Draws, clears, resolves and tiling are hooked and dropped (`draw.cpp`), and `BeginVertices`/`BeginIndexedVertices` hand out per-frame data-sink memory. `D3DQuery_GetData` (`query.cpp`) reports every occlusion query as visible, because the original waits for GPU-written counters (see [debugging.md](debugging.md)). The game runs through all five startup movies at a steady 30 presents a second with a black screen. A plume device and swap chain own the window and `Swap` presents a cleared frame, held to `target_fps`. `Direct3D_CreateDevice` still runs its recompiled body: it only fills in the guest `D3DDevice` struct that UE3's inlined code reads, and its `Vd*` calls land on the graphics system's no-ops. The two old frame-rate midasm hooks sat inside `Swap` and `SynchronizeToPresentationInterval`, so the cap and the FPS count now live in the present.
2. **Shaders** (in place). UE3 inlines `CreateVertexShader`/`CreatePixelShader` into `XeVertexShader_Create` and `XePixelShader_Create` (`src/gpu/hooks/shaders.cpp`), which bind each 0x102A11xx container to its D3D shader object; containers missing from the cache are dumped to `shader_dump/<hash>.bin`, and the cache is built from the dumps with the patched XenosRecomp ([shaders.md](shaders.md)). UE3 loads its shaders from cooked packages at runtime, so the corpus is collected by playing, not by scanning the XEX. Every shader created through the startup movies translates and loads as a module on both D3D12 and Vulkan.
3. **Draws** (first slice in place, `src/gpu/draw/`). The draw hooks capture each draw from the device shadow: shaders (`dev+0x3310`/`+0x330C`), the vertex declaration (`dev+0x2FD0`; count at `+24`, 12-byte elements at `+52`) or, since UE3 leaves that unset, the declaration and strides its single `D3DVertexShader_Bind` call bound the vertex shader with (a native `REX_HOOK` that records them and keeps the guest bookkeeping, without patching microcode), the vertex fetch constants (`dev+0x480 + 8*slot`, stream n at slot 95-n), the index buffer (`+0x18` address, `+0x1C` length, sign bit of `Common` for 32-bit, bits 29-30 the endian swap), the 256+256 float4 constants, the bool constants, `BlendControl0` and the VPORT registers. Every element is decoded on the CPU to four 32-bit values the way Bind's patch (`sub_829EC9C0`) defines the declaration type: number format from bits 8..9, the component selectors from bits 10..21, and selectors XOR 1 for 16-bit formats (type bits 6..7 = 01). The converted vertices and indices of each draw are cached across frames and kept in GPU buffers while the guest bytes they came from hash the same, so static meshes are neither decoded nor uploaded again. Fans, quad lists and rect lists are expanded; a rect list's fourth corner is v1 + v2 - v0, as UE3's unit square (0,0), (1,0), (0,1) in `sub_8297EBB0` shows. The present replays the frame through the bindless layout the translated shaders dictate, with the guest viewport scaled onto the window. Not yet: depth, cull, colour mask, alpha test, and depth-only (no pixel shader) draws, which are dropped. `BeginVertices`/`BeginIndexedVertices` draws are read once the guest has filled them. UE3's mesh draws all come through `0x82782340` → `RHIDrawIndexedPrimitive`.
4. **Textures** (2D in place, `src/gpu/textures/`). Each draw records the fetch constants (`dev+0x480 + 24*slot`) of the pixel-shader samplers that have a texture object bound (`dev+0x3278`); before the render pass the present resolves them to bindless 2D textures: base level untiled (Kameo's `texture_codec`, the standard Xenos tiling and packed-mip offset), endian-swapped, expanded where the host has no matching format, and uploaded through the frame's upload ring, with the fetch constant's swizzle as the view's component mapping and samplers built from its clamp, filter and anisotropy fields. Textures are cached by address, format, size, tiling, endian, swizzle and sign, and re-uploaded when an XXH3 of their guest bytes changes, which is what keeps Bink frames moving. The fetch constant's physical address is used as is (`0xA0000000 + address`); unlike Kameo it has not lost bits here. UE3's pool textures (filled through `XGSetTextureHeader`) need nothing extra. Not yet: mips, 3D and cube textures, the depth (`24_8`) and 16-bit-per-channel formats, which come from render targets, and evicting textures.
5. **Render targets and resolves** (colour in place, `src/gpu/draw/targets.cpp`, `replay.cpp`). Each guest surface (`Color0Info`/`DepthInfo` at `surface+0x1C`, size at `+0x24`) gets a host render target at the guest resolution, keyed by EDRAM base, format and size. Draws bind their colour and depth surfaces; `ClearF` and `Resolve` are recorded in order with the draws. A colour resolve copies the source target into a host texture the texture cache registers under the destination's address, so later fetches of that address sample it, and its clear flags (0x100 colour, 0x200 depth) clear afterwards. The present blits the texture `Swap` was handed (the resolved front buffer) onto the swap chain, letterboxed. Depth, stencil (`DepthControl`, `StencilRefMask` at `+0x2900`), cull (`ModeControl`), colour mask (`ColorMask` at `+0x28DC`), the window scissor (`+0x28C4`/`+0x28C8`) and the alpha test (as the shaders' threshold) are applied. Depth resolves (`flags & 7 == 4`) draw the depth target, read through a bindless descriptor, into an R32F render target (`depth_resolve.hlsl`). Resolve destinations come from texture objects, which hold virtual addresses, while sampled fetch constants hold the physical ones SetTexture computed; `TextureFetch::address()` canonicalises both the way D3D does. With that the WB, Kadokawa, Grasshopper and Unreal logos and the attract intro render correctly. Not yet: MRT, predicated tiling (logged if it ever runs), upscaling, and the readback consumers (`RHIReadSurfaceData`, real occlusion queries).
6. **Movies, gamma and UI.** Bink, `SetGammaRamp` as a present-time gamma pass, and the ImGui overlays drawn through plume.

## Graphics settings

The `Lollipop/Graphics` cvars, which the options screen's GRAPHICS page also sets ([../ui/option-menu.md](../ui/option-menu.md)):

| cvar | effect |
| --- | --- |
| `cherry_gfx_render_height` | Render resolution. 0 follows the window height, 720 is the console's. Host render targets at least 32 pixels on both sides are created at `S = height / 720` times their guest size (`GraphicsSystem::TargetScale`), and a resolve's destination at its source's scale; guest sizes still key both, so the capture side never changes. Smaller targets hold data the shaders compute from integer pixel positions, such as the 16x16 colour-grading LUT slices, and stay at 1x. Viewports (after the PixCenter half-pixel shift), scissors, clear rectangles and resolve rectangles are scaled at replay by their target's scale. Shaders get `g_InvResolutionScale`, the drawn target's, to turn `vPos` back into guest pixels, and `g_ScaledTextures`, a bit per pixel sampler whose texture is a scaled resolve plus `S` in 1/4096 units in its top half, so `tfetch2D` offsets and `getWeights2D` work in guest texels on scaled textures (the XenosRecomp patch, [shaders.md](shaders.md)). The slope-scaled depth bias is multiplied by the target's scale so it stays per guest pixel. A change drops every target and resolved texture once the GPU is idle. |
| `cherry_gfx_anisotropy` | 0 keeps each sampler's own; 2 to 16 forces that level on linearly filtered, mipmapped samplers. |
| `cherry_gfx_fxaa` | FXAA on the front-buffer blit (`blit.hlsl`), so it covers the HUD too. |
| `cherry_gfx_stretch` | The blit fills the window instead of letterboxing. |
| `cherry_gfx_vsync` | Present with vsync. Each frame is due 1/fps after the previous one's due time and takes the first vblank from half a refresh before it, so a rate the refresh does not divide (30 on 75 Hz) still averages out exactly. |
| `cherry_gfx_ultrawide` | 21 or 32 renders 21:9 or 32:9 (next launch). `XeInitD3DDevice` sizes the back buffer 720 lines tall and at most 1280 wide; two midasm hooks (`config/hooks/display.toml`) widen it and keep the 16:9 shadow-buffer budget instead of the 4:3 one. The camera is made hor+ in `src/engine/widescreen.cpp`: gameplay's `FPerspectiveMatrix_FOVXY` keeps the console's vertical FOV, and cameras that constrain their aspect, which the viewport would otherwise stretch because it always reports a desired 16:9, get their horizontal term narrowed in the main view (scene captures keep theirs). The HUD movies anchor to the wider edges by themselves. |
| `cherry_gfx_shadow_resolution` | 256, 512 or 1024 raise the game's character shadow maps from its ini's `MaxShadowResolution=128` (next launch; `src/engine/shadows.cpp`). A per-object shadow is projected radius x `ShadowTexelsPerPixel` clamped to that maximum and rounded down to a power of two, so the texels-per-pixel factor is scaled with it; both are re-asserted every tick. |

## Pipelines and constants

Draw pipelines are described by plain data (`src/gpu/draw/pipeline_state.h`), hashed, and cached in a hash map. Every pipeline built for the first time is appended to `pipelines.bin` beside the config, and at the next launch background threads build all of them while the game boots (`src/gpu/draw/pipeline_cache.cpp`), so a pipeline stalls a frame only the first time it is ever seen.

Each draw copies only the float4 constants its shaders read: XenosRecomp records one past the highest register the code reads (literals the shader defines excluded; 256 when a read is relative to a0, or to aL in a shader with loops) as `constantRegisterCount`, about 20 on average. Capture byte-swaps that many and replay fills that much of each stage's 4 KB block.

## Change detection

Textures and converted draw geometry are cached across frames and keyed by guest address; what decides whether the guest changed them is `src/gpu/guest_writes.cpp`. It sits on the SDK's one-shot write watches over guest physical memory (`EnablePhysicalMemoryAccessCallbacks`; the SDK's access-violation handler runs the callback on the writing thread). Each 4 KB physical page gets a stamp when written. A cache entry arms the watch over its bytes before hashing them and keeps the stamp it got. While no page in its range has a newer stamp, the entry is reused without reading the bytes again. A range in a view the watches do not cover (virtual memory below 0xA0000000, the 0xE0000000 view) is hashed every time, as is anything the guest rewrites with the same bytes, which would otherwise fault every frame.

## Native D3D library

Every D3D and XG entry point UE3 calls is a typed `REX_HOOK` (`src/gpu/hooks/`): draws and resolves (`draw.cpp`), render, sampler, viewport and scissor state (`state.cpp`), bindings, shader registration and ring data (`bind.cpp`, `shaders.cpp`), textures, surfaces and their layout arithmetic (`textures.cpp`), resources, locks, queries and predication (`resources.cpp`), waits (`sync.cpp`), the ring (`ring.cpp`) and the present (`present.cpp`). Each reproduces the guest-memory effects its recompiled body had and none of its ring packets; the behaviour of each was read from the game's own code in IDA. Guest calls they still make (XMemAlloc, critical sections) go through `cherry::core::CallGuest`.

Still recompiled: `Direct3D_CreateDevice` and its initialisation subtree (`sub_829FC210`, which reaches `Vd*` directly), `D3DResource_Destroy` (called when a resource's last reference goes) and the occlusion-slot allocator `sub_829EEB70`; UE3's tessellated quad patches (`D3DDevice_DrawTessellatedVertices`) are dropped and logged.

## ImGui overlays

`ReXApp` builds its overlays (F3 debug, F4 settings, backtick console) only for a graphics system with a presenter, or with no graphics system at all, so the native renderer gets none from it. `ReCherryApp::SetupPresentation` builds the same stack itself (`src/ui/overlay_stack.cpp`) and hands its `ImGuiDrawer` to `OnCreateDialogs`, which adds the F12 FPS readout. The toggles are `RegisterBind`s under the SDK's names (`bind_debug_overlay`, `bind_settings`, `bind_console`), dispatched by `ReXApp::OnKeyDown`, so saved keys carry over; F8 stays `bind_debug_frames`.

ImGui runs on the UI thread only, the thread its window input arrives on. After every present the render thread calls the request set with `GraphicsSystem::SetUiFrameRequest`, which posts one `CallInUIThread` (never more than one queued). There the drawer runs, and `PlumeImmediateDrawer` (`src/gpu/ui/imgui_drawer.cpp`) turns its draw lists into a `UiFrame`: non-indexed clip-space vertices with a texture id and scissor per draw, handed over with `SubmitUi` under `ui_mutex_`. The next `Present` takes the newest frame, or keeps the last one when none has arrived, uploads any textures registered since (`CreateUiTexture`, the font atlas), and draws it alpha blended over the swap chain image after the front-buffer blit and after the debug screenshot copy (`src/gpu/ui/ui_pass.cpp`, `ui.hlsl`). The present never waits for the UI. While an SDK overlay is open and ImGui wants the mouse or keyboard, the input system's active callback mutes the game's input, as `ReXApp` does. The compare build (`CHERRY_XENIA_COMPARE`) skips all of this and uses the SDK's own stack on the Xenia presenter.
